## Measurement and correctness audit

References below refer to the reviewed V0.94 source unless explicitly described as current documentation.

- **Normal browser paths and reset.** `tools/benchmark_browser.mjs:41` prepares U1385 through the built-in example and synthetic data through the ordinary project import input, sets the interval through the form, then creates a saved inactive-project launcher. `tools/benchmark.py:271` prepares a closed seed profile once, copies it into a separate disposable directory before every trial and launches a fresh browser. There is no cumulative deletion across repetitions. Preparation, profile copying and browser launch are excluded from open timing. OS file caches are not cleared.
- **Open boundary.** `tools/benchmark_browser.mjs:83` records `performance.now()` immediately before the project-card click. `tools/benchmark_browser.mjs:71` stops at the first poll that observes the expected project, enhanced first-section pixels, objects present, a clear busy indicator and saved state. This measures the documented first-section readiness boundary; it does not promise every image in the core has been decoded.
- **Edit/autosave boundary.** `tools/benchmark_browser.mjs:95` selects the lowest-numbered object through app state and dispatches Delete through the normal keyboard handler. It immediately requires object removal and dirty state, then observes saved/error state. The timer includes the handler and the 1,500 ms autosave debounce (`app/js/app.js:2821`), serialization and ordinary IndexedDB save (`app/js/app.js:2832`). The app's keyboard handler at `app/js/app.js:1750` reaches the regular deletion operation at `app/js/app.js:558`. Selection is automated; the write path is not substituted.
- **Analysis boundary.** `tools/benchmark_browser.mjs:123` checks resident label/exclusion masks, clears each row-count cache, and times calls to the app's exported `analyze` for all sections. UI rendering and result transport occur outside that timer. `tools/benchmark.py:113` decodes and crops the reloaded masks, applies the effective object-to-class lookup, then times calls to the public `sedcoretool.analyze_mask` separately using `perf_counter`. Imports, mask preparation and JSON serialization are outside Python analysis timing. API result/DataFrame construction remains inside it. JavaScript also executes the normal app analysis bookkeeping, so these are defined application/API observations rather than isolated language-speed comparisons.
- **Shared settings and mapping.** The exported effective lookup respects counted classes and candidate settings (`app/js/app.js:1004`). Adding one maps class index -1 to background 0 and indices 0..N-1 to Python classes 1..N. ROI/exclusion arrays are cropped consistently. Both fixtures have full-height vertical ROIs and nonoverlapping trace masks. Units, depth endpoints, 2 cm bins, 20% minimum valid area, retained partial bins and zero no-data padding agree. I inspected the corresponding aggregation formulas in `app/js/core.js:149`, `app/js/core.js:194` and `src/sedcoretool/pipeline.py:69`.
- **Reopen verification.** `tools/benchmark_browser.mjs:148` reloads after autosave and requires the object count to match, the deleted object to remain absent and its ID to be absent from every pixel in its original bounding box. The first warm-up exports these reloaded masks for Python. Each later browser trial must exactly reproduce the original edit record and all browser interval arrays (`tools/benchmark.py:296`), then compares with Python. This links persisted state to the numerical comparison rather than checking only a save-status label.
- **Floating point and categories.** `tools/benchmark.py:138` requires equal section/interval counts, equal column counts, exact BI/ii values and matching missing values. Depths, centres, valid-area percentage, total percentage and per-class percentages use the documented absolute tolerance of 1e-9. The synthetic case has eight no-data intervals and therefore exercises null categorical values. Additional direct guard probes rejected category mismatches, missing categories, missing numerical values and a 2e-9 percentage difference, while accepting a 5e-10 difference. No tolerance applies to categorical values.
- **RSS accounting.** `tools/benchmark.py:163` repeatedly enumerates descendants and samples `memory_info().rss`. For browser trials it sums the current Node driver's descendants at each collection, then retains the maximum sum; the Node driver and Python HTTP-server/orchestrator process are excluded. The normal driver launches only Chromium descendants. For Python it samples the launcher/descendants but returns the peak for the actual worker PID printed by `python_trial`, excluding a Windows virtualenv shim. `MIB = 1024**2` gives MiB. Collection spans process startup, input preparation and, for the browser, verification reload and shutdown, not only the individual timed actions. The 25 ms value is the wait target between collections, not a measured or guaranteed sampling interval; process enumeration adds overhead. Browser sample counts were 46–52 for U1385 and 60–62 for synthetic; Python counts were 11–12 and 17. Every run had samples.
