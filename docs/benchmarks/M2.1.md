# M2.1 Data table benchmark

This delivery covers the Data mode's initial table and one **Show more** expansion. The existing initial
400-row limit and 1,000-row increment remain the interaction boundary. It does not replace the table widget
or measure a fully expanded 100,000-row DOM.

## Acceptance criteria

- Prepare numeric values and interval labels only for rows included in the current display limit, across core
  boundaries. Keep the total row count accurate and export every source row, including undisplayed ones.
- Preserve row numbering, column order, native text selection, editing/restoration, core choice and interval labels.
  Compare exported values exactly with the deterministic fixture, including missing values and half-open intervals.
- On the 100,000-row fixture, reduce the median **Allow editing values** render latency by at least 30% against
  the baseline. Record all runs and the other operation timings; do not claim a scroll or export improvement
  unless the measurements support it. Use one warm-up and five measurements per size, plus a separate CPU profile.
- Pass the repository checks and browser regression. Keep further table or full-DOM work separate.

## Reproduction

Use the dependencies and environment setup of [M0.1](M0.1.md). From the repository root:

```sh
python tools/benchmark_data_table.py --chrome "/path/to/chrome" --output ../m21-local.json
```

`--case small|medium|large` selects one size. Defaults are one warm-up and five measurements. Each trial starts
a fresh headless Chrome profile at 1,440 × 900 and prepares its fixture before timing. The benchmark uses
2,000, 20,000 and 100,000 total rows, divided equally between two cores. Six numeric columns use deterministic
integer arithmetic with seed constant 210108; every 37th row is missing. Depth is the row index, age is twice
that index. Two interval layers alternate categories in nonoverlapping 100-row bands. All cores and layers
are selected. The JSON records fixture dimensions, runtime versions and source fingerprints.

## Measurement boundaries

Opening starts immediately before clicking the Data toolbar button and includes core refresh, row construction,
HTML assignment and forced layout. Edit mode and Show more start immediately before their respective control
clicks. Each visual timer ends after two animation-frame callbacks, so refresh-rate and scheduling delays are
included. Selection focuses a rendered editable numeric cell and selects its text with the native DOM Range API;
it does not measure pointer travel. Scrolling moves the table wrapper to its bottom and waits for the same
two-frame boundary. Show more is measured once, expanding the DOM from 400 to 1,400 rows.

CSV timing starts at the export click and ends when the normal download path creates its Blob. Disk download,
Blob reading, parsing and verification are excluded from that timer. Every exported cell is then checked against
the fixture. The SHA-256 covers the complete CSV without provenance comments; these comments contain delivery
and timestamp metadata. A separate CPU-profile trial attributes sampled self time to function/source locations
during the visual operations, excluding CSV export. Profiling is excluded from the timing summaries.

Peak RSS uses the [M0.1 sampler and limitations](M0.1.md#measurement-boundaries). Its collection covers the entire
browser trial, including setup and full CSV validation; it is not an isolated allocation measurement of the
table model. The report retains the sampling count and MiB units. Comparisons apply to this machine, headless
browser and fixture. No CI performance thresholds are introduced.

## Recorded comparison

The [V0.108 baseline](M2.1-v0.108-baseline.json) and [V0.109 displayed-prefix run](M2.1-v0.109-prefix.json)
use the same fixtures, benchmark tools, Windows 11 / Ryzen 7 7700X machine, Chrome 157.0.8103.40,
Node 22.23.4 and Puppeteer 23.11.1. Each has one warm-up and five measured trials per size plus a separate
profile trial. Every CSV row was checked, and all three complete CSV fingerprints match before and after.
Both reports retain the original precision, full ranges and RSS observations.

The runs precede the delivery commit. The baseline source is `adab0bb80e7e8cfac639a0dc29a7fcfff394fefa`
with the three benchmark files from this delivery: `tools/benchmark_data_table.py`,
`tools/benchmark_data_table.mjs` and `tools/data_table_fixture.mjs`. Its aggregate fingerprint was reproduced
from that commit's Git archive plus these files. The candidate report records the delivery's measured source
fingerprint, including its V0.109 version stamps. Both record a dirty tree because the tools and delivery were
not yet committed; use the fingerprints, not the parent commit alone, to identify the measured source.
A final formatting cleanup removed one empty line at the end of `tools/data_table_fixture.mjs`. To reconstruct
either measured fingerprint from the delivered tools, append one LF to that file after CRLF normalisation.
This is the only source difference after measurement, and both reconstructed fingerprints were checked.

Median elapsed times in ms:

| Rows | Open, before → after | Edit mode, before → after | Show more, before → after |
|---:|---:|---:|---:|
| 2,000 | 48.0 → 47.5 | 58.4 → 51.9 | 116.8 → 116.8 |
| 20,000 | 66.9 → 55.0 | 62.5 → 50.7 | 133.2 → 116.9 |
| 100,000 | 145.3 → 88.9 | 96.3 → 52.4 | 183.2 → 133.2 |

The large-case edit-mode median is 45.6% lower, meeting the predeclared 30% criterion. Opening is 38.8% lower
and the single expansion 27.3% lower on this fixture. The separate baseline profile attributes 106.4 ms of
sampled self time to the per-row layer lookup during the visual operations; row construction also appears
prominently. The correction bounds those operations to the displayed prefix. It does not virtualise the DOM.

Selection and scrolling remain near the two-frame floor (about 33 ms). No improvement is established for them.
CSV median latency increases from 4.6 to 4.9 ms, 33.5 to 36.2 ms, and 163.2 to 179.4 ms. The large-case ranges
are 161.6–174.8 ms before and 174.9–185.5 ms after. Full export still prepares all rows and is not optimised by
this delivery; the measured export cost is a limitation of the result. The different allocation/JIT histories
of the visual operations may affect its later timing, but these runs do not establish a cause. Whole-trial
peak RSS is similar (large-case medians 811.5 and 818.6 MiB); no isolated memory reduction is claimed.

The browser regression separately counts numeric-array accesses during an edit-mode rebuild: 400 × 6 values
are read for a 2,400-row project. It also checks one expansion across a core boundary, full CSV after edit and
restore, selection, filters, and empty/age-only cores. This probe is not active during benchmark timing.
Further expansion can still produce a large cumulative DOM. That path and the full-export cost need their own
measurements before introducing viewport rendering or changing selection, navigation or interval-query behaviour.
