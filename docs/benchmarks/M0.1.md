# M0.1 performance baseline

Run from the repository root with a clean checkout, Python 3.10 or later, Node 22, and Chrome or Chromium. Use
an isolated Python environment if the checkout does not already have one.

```sh
python -m pip install -e . psutil==7.2.2
npm install --no-save --package-lock=false puppeteer-core@23.11.1
python tools/benchmark.py --chrome "/path/to/chrome" --output ../m01-local.json
```

Pass the Chrome executable path for the platform, for example `C:\Program Files\Google\Chrome\Application\chrome.exe`
on Windows. The default run uses one warm-up and five measured repetitions for each case. The JSON report contains
every run, the median and full range of the measured runs, the environment, the input fingerprints and the numerical
comparison. `--case u1385` and `--case synthetic` select individual cases for diagnosis.

## Fixtures and settings

- **U1385I-1H.** The built-in IODP example creates and saves a project from the six local archive-half JPEGs and
  the two physical-property CSVs. Preparation uses the example's normal levels preset and candidate detection.
  The analysis includes candidates and uses each section's example ROI, with a 10% horizontal margin on both sides.
  See the [example's source and depths](../../examples/U1385I-1H/README.md).
- **Synthetic.** NumPy PCG64 seed 138501 creates eight 960 × 6,400 pixel sections, each 128 cm deep. Each section
  contains seeded grayscale JPEG texture and nonoverlapping rectangular traces in two classes, a central ROI with
  a 20 px horizontal margin, an excluded full-width band and a partially excluded block. The generator writes
  a project package with preset masks and trace geometry, which the app imports through its ordinary file input.
  It uses unfiltered working images at original resolution.
- Both use 2 cm intervals, a minimum valid area of 20%, a retained partial final interval, and zero extra
  padding around intervals with no data. The lowest-numbered trace in the first section is deleted in each trial.
  The report lists the section dimensions, depth units, ROIs, filters, detection settings and trace counts
  after the edit.

## Measurement boundaries

Each case is prepared once in a disposable Chrome profile served from loopback. Preparation ends by creating a
small empty project so that Chrome starts at the library with the target project saved but inactive. Before every
trial, the closed seed profile is copied and opened in a new headless browser process at 1,440 × 900. The copy is
discarded afterward.
The profile is reset for each run, and the operating system file cache is left in its ordinary warmed state.

| Metric | Included work |
| --- | --- |
| Browser open | From clicking **Open** in the library to the first browser poll that sees the project loaded, its first section's enhanced pixels ready, and the busy indicator cleared. Excludes Chrome launch, profile copy and fixture preparation. |
| Browser autosave | From dispatching **Delete** on the selected trace to observing the saved status after the normal IndexedDB autosave. Includes the debounce, the edit and the write. |
| JavaScript analysis | Calls the app's `analyze` on all sections with resident masks and cleared row-count caches. Excludes the UI rendering, mask preparation and result transport. |
| Python analysis | Calls the public `sedcoretool.analyze_mask` on all sections of the same edited project. Excludes process startup, mask decoding and result serialization. |
| Browser peak RSS | Maximum sampled sum of RSS across Chromium descendants of the Node driver during the trial, including launch and the verification reload. Excludes Node and the benchmark's local HTTP server. |
| Python peak RSS | Maximum sampled RSS of the process that actually runs Python analysis, including imports and input decoding. The worker reports its PID so the orchestrator and any virtual-environment launcher are excluded. |

Browser durations use `performance.now()` and Python durations use `perf_counter()`. Memory is recorded in
MiB (1,048,576 bytes). The orchestrator samples RSS with [psutil](https://psutil.readthedocs.io/stable/) and waits
up to 25 ms between collection attempts. The number of samples is in the report. Peaks between samples can be
missed, and summing Chromium processes can count shared resident pages more than once. The OS, CPU, RAM, runtime
versions, checked-out commit and a SHA-256 of the measured source and input files are recorded in JSON. The hash
includes tracked app, Python package and IODP example files plus the two benchmark scripts, with CRLF normalised
in text files.

## Verification

The driver selects the target through the app's test hook and uses the normal keyboard handler to delete it.
Every trial reloads the saved project and checks both the absence of the deleted object and its absence from the
mask in its original bounding box. The first warm-up exports the reloaded masks, ROIs and effective class mapping
to a temporary input for the Python worker. Python crops to the same ROI and remaps object IDs to class IDs before
measurement. Each trial checks that the browser returns identical interval results to the warm-up and compares
them with Python. Depth boundaries and centres, valid area, total bioturbation and per-class percentages use
an absolute tolerance of `1e-9` in depth units or percentage points, to allow floating-point rounding between
the two implementations. Section and interval counts, missing values, BI and ii must agree exactly. The two
fixtures have nonoverlapping trace masks.

The benchmark uses existing browser automation and adds only psutil to the Python environment used to run it.
OS-specific process APIs could remove that dependency at the cost of separate Windows, Linux and macOS samplers
and their maintenance. Neither package is loaded by SedCoreTool at runtime or shipped with the desktop app.

## Recorded run

The [V0.94 report](M0.1-v0.94.json) contains the measured runs on Windows 11 with an AMD Ryzen 7 7700X.
The run took place before the delivery commit so that the tool and its results could ship together. The
report records the parent commit and the input-file fingerprint of the measured V0.94 working tree. That
fingerprint identifies the measured inputs when reproducing the benchmark from the delivery commit.
