# M3.1.2 analysis profile

## Predeclared scope and acceptance

Authorised by the maintainer on 10 November 2026. Editor: Codex; verification: automated regression checks
and reproducible author measurements. No independent reviewer is assigned. This phase measures the existing
analysis and selects a subsequent optimisation candidate; it does not change scientific algorithms or defaults.

- Reuse M0.1's public U1385I-1H and eight-section, 960 × 6,400 synthetic fixtures (PCG64 seed 138501).
  Prepare through the existing browser driver, delete its defined first trace, save normally and verify reload.
  Record the edited masks, effective class mapping, exclusions, ROI, settings and input/result fingerprints.
- Measure the application `analyze` with resident masks and cleared row-count caches, then with reusable
  row counts. Measure the pure `rowCounts` and `binRows` stages separately and verify their output against
  the application. Run both the baseline 2 cm intervals and 1.37 cm intervals to exercise fractional pixel
  boundaries and partial final intervals. The minimum valid area remains 20%; no-data padding is zero.
- Measure the public Python `analyze_mask` on matching cropped and remapped masks. Exclude decoding,
  remapping, serialization and process startup from analysis timing. Record elapsed and process CPU time.
- Use one warm-up and five measured fresh-process trials per case. Report every trial, medians/ranges,
  per-section costs, environment and provenance. Keep diagnostic CDP/cProfile trials separate from timing
  trials, and record their repetition counts and attribution limits.
- Require exact JavaScript results across cold/cached/stage paths and repetitions. Compare JavaScript and
  Python depths and percentages with the M0.1 absolute tolerance of 1e-9, allowing only floating-point
  operation-order differences; require exact section/interval counts, missing values and BI/ii.
  Verify unchanged input masks after measurement and preserve the legacy numerical regression suite.
- Reuse M0.1's 25 ms target RSS sampler. Browser RSS sums Chromium descendants, excluding the Node driver;
  Python RSS counts the actual worker PID. These peaks cover each complete worker lifetime, including
  opening/decoding and verification; they do not isolate analysis allocations. Report sample counts.
- Record the measured application commit and a normalised source hash separately from benchmark-tool
  hashes. Reject source/tool changes during measurement. Publish complete raw evidence and limitations;
  claim no speedup and set no CI performance threshold in this profiling phase.

## Diagnostic amendment before the full run

The initial public-case diagnostic failed the predeclared fractional parity check: the first 1.37 cm
interval in section 2 ends at 1.5138 m in JavaScript and 1.5136 m in Python. This is a scientific disagreement,
not acceptable roundoff under the 1e-9 tolerance. The original criterion above remains recorded.
The profiling run therefore keeps 2 cm parity mandatory and records fractional failures explicitly, with
both complete interval arrays, every differing cell and independent result fingerprints for each runtime.
Both runtimes must repeat their own results exactly, including the separate CPU trials. `complete` describes
completion of measurement; the separate `scientific_parity_passed` flag reports scientific acceptance.
Correcting scientific boundaries belongs to a subsequent delivery, before optimisation, rather than changing
the measured implementation in this profile. No tolerance is widened and failed parity is never labelled a pass.

## Reproduction

Use the existing Python analysis dependencies plus psutil, Node 22, puppeteer-core 23 and Chrome/Chromium,
as for [M0.1](M0.1.md). No application dependency is added.

```sh
python tools/benchmark_analysis.py --chrome "/path/to/chrome" --output docs/benchmarks/M3.1.2-v0.120.json
```

`--case u1385` or `--case synthetic` selects one fixture. `--workspace` selects a parent for disposable
profiles. Defaults are one warm-up and five measured repetitions. The output is published by atomic
replacement after each completed case, with `complete: true` only after both the selected cases and final
provenance verification succeed.

## Measurement boundaries

Fixture preparation uses `tools/benchmark_browser.mjs` unchanged. Its ordinary Delete/autosave/reload sequence
produces the edited seed profile and an RLE snapshot. Each timing trial copies that closed profile into a
fresh browser process, loads its saved project and forces the existing masks resident before measurement.
The application memory budgets are unchanged. The same cropped ROI and effective object-to-class mapping
are prepared as NumPy arrays before calling the public Python API in a fresh worker.

- **Browser cold:** one synchronous sweep of `analyze` over all sections, after deleting each `_rc` row-count
  cache. The timer includes class mapping/signature, pixel counts, binning and normal age/manual enrichment;
  it excludes opening, input verification, result serialization, painting and result transport.
- **Browser cached:** twenty consecutive sweeps in the same synchronous task, divided by twenty. Existing
  counts are reused but class mapping/signature, binning and enrichment still run. The full bin objects must
  exactly equal the cold result. This measures repeated calculation, not the responsiveness of a UI action.
- **Direct stages:** after those sweeps, separately time effective-class mapping, `rowCounts` and `binRows`
  once per section. Verify every integer row count and shared interval value against application results
  outside timing. These later measurements have different cache/JIT/allocation conditions and are not an
  additive decomposition of the earlier cold time. Per-section values remain in the raw report.
- **Python:** time one sweep of `analyze_mask` with `perf_counter` and `process_time`, including validation,
  row/bin counts, classification and DataFrame construction. Decode/remap before timing and serialize after
  it. Additional per-section measurements follow separately and must reproduce the full-sweep results.
- **CPU diagnostics:** one additional fresh-process trial per case, excluded from timing/RSS statistics.
  CDP samples at a requested 1,000 µs interval during twenty cold and two hundred cached browser sweeps per
  interval setting. Self-sample weights include runtime/GC/program activity between profiler start/stop;
  they are not instrumented function durations. cProfile records five Python sweeps per setting, including
  native reductions where attributed by CPython. Self time and cumulative time must not be added together.
  The `~` source in the raw Python profile denotes native/built-in profiler entries.

Both settings run sequentially (2 cm first) in each worker. Input hashes are checked before/after; each
runtime must repeat its interval fingerprints exactly in all six unprofiled trials and the CPU trial.
Browser masks and results at 2 cm also match the accepted clean M0.1 fingerprints. The Python API has no
matching reusable row-count cache; its full calls and the cached browser calls are different workloads.

## Fractional boundary finding

The public fixture's sections 2 and 4 each have 7,450 ROI rows over 1.49 m. In section 2 the stored endpoints
are 1.5 and 2.99 m, giving a floating-point span of `149.00000000000003` cm. The implementations evaluate:

```text
JavaScript: bin_cm * (n_rows / span_cm) = 68.5
Python:     (bin_cm * n_rows) / span_cm = 68.49999999999999
First edge: floor(bin_px + 0.5)        = 69 versus 68
```

Reproduce the arithmetic in Node without any image decoding:

```sh
node --input-type=module -e "const s=(2.99-1.5)*100; console.log(1.37*(7450/s), (1.37*7450)/s)"
```

Across the public core, 216 corresponding intervals contain 805 differing cells. Maximum depth difference
is 0.00020000000000131024 m; maximum percentage difference is 0.7675689880128473 percentage points.
Two BI values and one ii value differ. All six unprofiled repetitions reproduce identical differences;
the diagnostic trial repeats each runtime's own fingerprints exactly. This is not a timing failure or
JPEG-decoder difference. No precision tolerance is relaxed, and the raw report explicitly sets
`scientific_parity_passed: false` while `complete: true` records completion of measurement.

The original fractional-parity acceptance criterion is unmet. M3.1.2 remains in review for scientific
acceptance; the next proposed phase is M3.1.3, to agree and apply one canonical conversion order with
cross-language half-row/adjacent-float regressions. Only after that correction should a performance phase
compare row/class-count alternatives against this profile and the M0.1 scientific reference.

## Limits and delivery validation

The fixtures cover nonoverlapping labels, exclusions, twelve/four named classes, partial intervals and
default indices. They do not profile overlapping class layers, custom Python schemes, nonzero no-data
padding, populated manual/age enrichment, hundreds of classes, tiled/16-bit processing or nonresident masks.
Existing regression tests cover additional numerical contracts but do not establish their performance.
Browser timers have finite resolution; near-zero class-mapping measurements and short per-section stages
should not be interpreted precisely. Windows process CPU measurements are visibly quantised. Normal
desktop load and operating-system caches are uncontrolled; there is no cross-platform performance claim.

Delivery checks: 193 Python tests passed, six optional/permission skips; 152 Node tests passed; JavaScript
types, Ruff, version consistency, diff whitespace and the standalone build pass. The new browser benchmark
exercises ordinary fixture preparation, deletion, autosave and persisted reload before profiling; no
interface or save implementation changes in this delivery. The full interface smoke suite is not repeated
on the unchanged V0.119 interface. No optimisation, scientific correction or default promotion ships here.
