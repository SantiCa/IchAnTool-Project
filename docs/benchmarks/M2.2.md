# M2.2 large-image profiling

## M2.2.2 contract and acceptance criteria

The maintainer authorised the next roadmap phase on 10 November 2026. This delivery measures existing opening,
section navigation and viewport interaction before selecting an optimisation. It does not change the image
loader, cache budgets, working resolution, algorithms or program defaults.

Use the public U1385I-1H example and the existing M0.1 synthetic project (eight 960 × 6400 sections, seed 138501).
Add eight 960 × 16000 synthetic sections with the same generator/settings and 128 cm per section. This third
case contains 122,880,000 working pixels: original plus enhanced RGBA arrays alone occupy 983,040,000 bytes,
above the application's 900,000,000-byte pixel-cache budget. Its 614,400,000 bytes of uncompressed label and
exclusion masks likewise exceed the 500,000,000-byte mask budget. No private data are used.

Before measuring, prepare the project through the normal example/import path and save an inactive launcher.
Copy the closed seed browser profile for every trial. Run one warm-up and five measured trials per case;
leave OS file caches in their ordinary warmed state. The benchmark must:

- Record the measured application commit and a normalised source fingerprint, whether its app/package files
  match that commit, benchmark-tool hashes, environment/runtime versions and fixture/result fingerprints.
- Measure library opening to the M0.1 readiness boundary (enhanced first section, busy clear and saved status),
  then separately through two animation frames. Exclude browser launch, preparation and profile copying.
- Measure ordinary section-select changes through pixel readiness and two animation frames. Visit sections
  1 through N−1, then 0, N−1 and 0. Record pixel/mask residency before every selection, cache state afterward,
  individual latencies, total navigation and resident/nonresident categories. Do not assume a return is warm.
- Measure three zoom-button actions and three middle-button pan moves through two animation frames. Report
  wall latency separately from CPU sampling; browser dispatch/protocol and frame scheduling are included.
- Sample the simultaneous Chromium process-tree RSS sum at the M0.1 25 ms target cadence, excluding Node/server.
  Report the whole-trial peak and sample count, including export/reload verification. RSS can double-count
  shared pages and miss between-sample peaks; it is not a cache-allocation or steady-state measurement.
- Collect a separate diagnostic main-thread and available dedicated-worker CPU profile; exclude profiled
  runs from latency summaries and describe any worker-attachment gap.
- Check depth↔row round trips at representative ROI positions within 1e-9 working pixels; check complete
  interval arrays, masks and image buffers for exact equality where repeated. This tolerance covers only
  arithmetic rounding in the inverse depth formula, not measurement/percentage changes.
- Delete a trace through the normal handler, undo and redo it, save/reload and verify the persisted edit and
  unchanged remaining interval results. Export a full-resolution mask PNG through the normal button and
  compare every decoded pixel with the current effective labels/exclusions, with exact equality.

Acceptance is a reproducible report with all runs, median/range, source provenance, correctness checks and a
source-backed interpretation that identifies the next measured target and explains whether tiled loading is
justified. No speedup or CI performance threshold is claimed by profiling alone. Independent review was
required for M0.1; this phase does not replace or reopen that accepted baseline.

## Reproduce the profile

From the repository root, with its Python package and existing benchmark dependencies available:

```powershell
$env:PYTHONPATH = (Resolve-Path src).Path
python tools/benchmark_images.py --chrome "C:/Program Files/Google/Chrome/Application/chrome.exe" --warmups 1 --repetitions 5 --output ../m22-local.json
```

Use the browser path for the platform. Dependencies are those of M0.1: Python with NumPy, pandas, Pillow and
psutil, Node 22 and puppeteer-core 23.11.1. `--case u1385`, `--case synthetic` and `--case large` select individual
cases. `--workspace` optionally chooses a parent for disposable profiles/fixtures; the default is the system
temporary directory. Each case also runs a separate CPU-profile trial, which is excluded from the timing/RSS
summaries. Reports are replaced atomically after complete cases and marked `complete: true` only after all
selected cases finish and the application/tool provenance still matches the start of the run.

Preparation reuses `benchmark_browser.mjs` and the ordinary example/import, interval-setting, project-creation
and library controls. Each measurement uses a fresh browser process and a copy of the closed seed profile;
there is no cumulative deletion. The V0.116 first-project correction is necessary to exercise these normal
paths from a fresh library. Timed opening uses the same readiness condition as M0.1, with a separate two-frame
boundary. The animation-frame boundary confirms browser drawing opportunities, not physical monitor latency.
Operating-system file caches are not cleared.

Every selection records whether original pixels and each mask were already resident. A cache-state sample
lists resident pixel indices and indices with any resident mask, and sums only original/enhanced RGBA buffer lengths. That sum excludes
thumbnail canvases, browser/native image allocations, packed masks and other caches; it is distinct from the
sampled whole-trial Chromium RSS. Zoom/pan timings include the driver/browser dispatch and two frame callbacks.

Main-thread CPU sessions are separate for opening and navigation/interaction. Initial image hashing and
the scientific-input snapshot occur outside those sessions; subsequent cache-state reads remain in the
navigation session. Worker profiling begins when the worker session is available and can miss its first task
during attachment. Worker self-samples cover both stages and idle gaps. Profiles are diagnostic samples,
not exact elapsed-time accounting; rank named application sites separately from idle/runtime/driver entries.

The input/result checks include all intervals and packed masks, source/enhanced first-section image buffers
before and after navigation/reload, depth/row round trips, delete/undo/redo and unchanged unaffected intervals,
persisted project reload, and every decoded RGBA pixel of the full-resolution exported mask. Hash equality is
exact within the recorded environment. Native JPEG decoding and PNG encoding can vary across browser/library
versions, so cross-environment byte equality is not assumed.
Object selection for the edit uses the public test hook; deletion, Undo, Redo and export use ordinary handlers.
These workloads open prepared JPEG projects with saved working-resolution masks. They do not measure initial
TIFF/BigTIFF ingestion, 16-bit enhancement, changing the working resolution or extremely wide image layouts.

## Recorded results

The [complete report](M2.2-v0.116-profile.json) measures application **V0.116**, commit
`0ecb5efb7b4fc51c62b6781511a26444fae4f1fb`. Every measured application/package file matches that commit after
normalising text line endings, including bundled licence texts. The whole working tree was dirty because the
new benchmark tooling was not yet committed; its separate hashes are recorded. The
[author source/statistics audit](M2.2-source-audit.json) verifies those hashes, recalculates every summary and
checks the generator. It is not an independent review. The tools/report ship in V0.117; its application change
relative to the measured delivery is the version metadata.

Environment: Windows 11 10.0.26300, Ryzen 7 7700X (8 cores/16 logical CPUs), 31,850 MiB RAM; Python 3.12.4,
NumPy 1.26.4, pandas 2.2.2, Pillow 11.3.0, psutil 5.9.0; Chrome 157.0.8103.40, Node 22.23.4,
puppeteer-core 23.11.1. The command above ran all three cases with one warm-up, five measured trials and one
separate CPU-profile trial each. All 21 browser trials passed the input/result, depth, edit, export and reload
checks. Each full-resolution PNG comparison checked 2,595,000 pixels for U1385, 6,144,000 for synthetic and
15,360,000 for large.

| U1385 (15,228,500; 8) | 179.7 [174.7–195.5] | 300.0 [291.0–310.9] | 902.5 [866.8–942.0] | 1208.6 [1205.6–1258.7] |
| Synthetic (49,152,000; 10) | 355.0 [347.8–365.6] | 489.2 [478.6–505.9] | 1974.7 [1963.6–2056.6] | 2170.4 [2114.1–2182.2] |
| Large (122,880,000; 10) | 872.8 [864.6–881.1] | 1306.0 [1297.3–1323.9] | 4805.4 [4765.4–4887.1] | 3385.4 [3211.2–3429.2] |

The first return to section 0 stayed resident in U1385 and synthetic: medians 32.3 and 32.2 ms. In every large
trial that section had been evicted; its first return took 281.4 ms [265.6–299.0]. After reloading it, the final
resident return took 32.3 ms [32.1–32.5]. The large navigation traces plateau at five resident original/enhanced
section pairs; cache accounting also includes canvases. Three zoom actions totalled about 97 ms and three
pan moves about 146 ms per case. Those totals include frame/protocol scheduling and do not establish minimum
render-only latency. RSS includes the full-resolution export and verification reload; it is not the resident
pixel-buffer footprint.

The default synthetic fixture is byte-identical to the unparameterised V0.116/M0.1 generator when both execute
with the recorded dependencies (SHA-256 `aadd7befe779ba54dd8cf00afdc5ae0007162150b7e354a14ab4bddcf6d9bfbb`).
Its archive hash differs from the historical M0.1 report, which used different Python/NumPy/Pillow versions.
The same construction, dimensions, seed and settings are reused; historical archive byte identity or a
direct timing improvement over M0.1 is not claimed. The opening/navigation boundary, browser state and
environment in this report define the comparison baseline for the next experiment.

## Interpretation and next experiment

The largest named main-thread navigation site is `columns.js::reduceRGBA`: sampled self-times are 185.8,
554.9 and 1517.0 ms in the separate U1385, synthetic and large diagnostic trials. Callbacks in the same module
and `sectionCanvas` add further work. Source inspection connects this path to `app.js::drawNav`: its narrow
navigation strip requests `sectionCanvas`, which prepares a column-width raster (up to 512 pixels wide) by
scanning the source image and trace masks before drawing the much narrower visible strip. The large trial's
worker filter callback accounts for about 575.7 sampled ms across opening and navigation; main-thread `render`
accounts for 118.4 sampled navigation ms. These are self-samples from a different trial, not percentages of
the elapsed medians above.

**The next target is navigation-strip thumbnail preparation.** An opt-in, separately cached preview sized for
the displayed navigation strip is a smaller first experiment than a new tiled loader. Keep column/figure
image preparation and scientific analysis contracts intact, and compare with this same benchmark. The
experiment must predeclare its visual-equivalence criterion, verify click/drag depth mapping, retain exact
measurement/mask-export results and demonstrate lower first-visit latency before default promotion.

Tiled loading remains an option for other inputs, especially full-resolution/16-bit TIFF workloads outside
this measurement. These results do not yet justify its implementation ahead of the identified navigation
preview work. No loading/cache-budget/working-resolution optimisation or acceleration dependency is shipped
by the profiling delivery; M2.2 remains open for the measured experiment.
