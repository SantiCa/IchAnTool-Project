# M1.1.2 editing-history benchmark

Use the same Python, Node, Chrome and benchmark dependencies as [M0.1](M0.1.md). Run from the repository root.

```sh
python tools/benchmark_history.py --chrome "/path/to/chrome" --output ../history-local.json
```

The defaults are one warm-up, five measured repetitions and one separate CPU profile for each case. Use
`--case sparse` or `--case dense` to isolate a case, and `--cycles` to set the number of Undo and Redo cycles.
The report records the runtime, hardware, source commit and input fingerprint. Every trial creates a fresh
Chromium profile and imports a deterministic project through the usual project picker. No user project is used.

## Workload

Both cases use a single 1,024 × 1,024 section, a full-image analysis region and a uniform generated PNG. The
fixtures contain 256 or 8,192 traces laid out as 6 × 6 px squares on a 10 px grid, plus one trace underneath one
pixel in each of the first 36 squares. The two cases have the same raster size and change the same pixels.

A trial deletes the first 36 traces to exercise the 30-step cap. It then runs eight cycles of 30 Undo
and 30 Redo actions using the editor buttons. The timed workload includes 36 deletions, 240 Undo actions
and 240 Redo actions. The harness checks affected pixels and overlap order after each batch and verifies that
the full history has the same payload at the first and last checkpoints. It then undoes 15 steps outside the
latency measurement, so both directions hold 15 steps at the combined heap measurement. The mixed state is
saved and verified after reloading, with both history directions empty.

Through V0.103, the driver reapplied deletions as new edits in place of native Redo and measured heap with all
30 steps on Undo. To reproduce those runs, use the driver from the corresponding versioned commit.

## Measurement boundaries

| Metric | Method |
| --- | --- |
| Action latency | Browser `performance.now()` around the synchronous Delete event or Undo or Redo button click. Includes the app's handler and its synchronous rendering work. Fixture setup, selection, inter-batch frames, deferred rendering and autosave are outside the clock. The report includes each run's median, nearest-rank p95 and range. |
| History heap | After the last normal autosave, force GC in the page and measure V8 used heap with Chrome DevTools. Repeat after removing only the trace records from both directions, and again after removing the remaining steps. The differences estimate retained trace-record memory and the remaining history while the live project stays open. |
| Process memory | The M0.1 sampler records peak summed RSS of Chromium descendants, including launch, setup, the long session, GC and reload. It waits up to 25 ms between collection attempts. Shared pages can be counted more than once. |
| CPU attribution | A fresh trial requests 100 µs samples through the Chrome DevTools profiler. The report sums sampled time under `deleteObjects`, `beginOp`, `undo`, `redo` and `swapEditStep`, including calls beneath each frame. These totals can overlap. Earlier runs attributed replay to `undoOne`, and `beginOp` included full trace snapshots through V0.102. |

Heap differences are estimates from one renderer isolate. They count allocations that become collectible in
each intervention, including references retained solely by history. The report also records object record
counts, changed pixels and distinct overlap arrays in the history. The sampled process peak includes the
whole browser tree and has a different scope from retained heap. CPU profile samples provide approximate
attribution separately from the unprofiled action latencies. The workload models repeated small edits.

See the DevTools protocol definitions for [used heap size](https://chromedevtools.github.io/devtools-protocol/tot/Runtime/#method-getHeapUsage)
and [CPU sample timing](https://chromedevtools.github.io/devtools-protocol/tot/Profiler/#type-Profile).

## Recorded run

The [V0.97 report](M1.1.2-v0.97.json) records each run on Windows 11 with an AMD Ryzen 7 7700X and Chrome
156. At the first and final full checkpoints, both histories held 30 steps and 1,080 changed pixels.
The median retained heap was 0.61 MiB in the sparse case and 19.68 MiB in the dense case. The dense case
retained 19.66 MiB through its object snapshots. The separate dense CPU profile attributed about 25.5% of the
sampled deletion time to `beginOp`, from 96 samples within that function. The sparse estimate had four
`beginOp` samples.

The measurements were taken before the delivery commit so the scripts and results could ship together. The
report lists the parent commit and the fingerprint of the measured V0.97 inputs. Use the fingerprint to verify
the measured inputs from the delivery commit.

## M1.1.3 trace deltas

The same command and workload were run on [V0.102](M1.1.3-v0.102-baseline.json) and
[V0.103](M1.1.3-v0.103.json), with one warm-up, five measured runs and one separate CPU profile per case
and version. Both browser builds ran on the same Windows 11 machine with an AMD Ryzen 7 7700X,
Chrome 156.0.8078.80, Node 22.23.4 and Puppeteer 23.11.1. The V0.102 browser was served from a clean
checkout. The shared Python benchmark environment reports the V0.103 package in both runs. The history
workload and correctness checks execute in the browser. The V0.103 report was recorded before committing
the delivery and includes the fingerprint of the measured inputs.

| Traces | Browser build | Trace records at cap | History heap (MiB) | Trace records (MiB) | Browser peak RSS (MiB) | Delete (ms) | Undo (ms) | Reapply (ms) |
| ---: | :--- | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| 257 | V0.102 | 7,095 | 0.6117 | 0.5835 | 626.1 | 0.30 / 1.20 | 0.30 / 0.60 | 0.20 / 0.50 |
| 257 | V0.103 | 30 | 0.0827 | 0.0545 | 633.6 | 0.30 / 1.30 | 0.20 / 0.50 | 0.20 / 0.40 |
| 8,193 | V0.102 | 245,175 | 19.6840 | 19.6558 | 749.2 | 0.90 / 4.10 | 0.60 / 2.30 | 0.70 / 2.20 |
| 8,193 | V0.103 | 30 | 0.0748 | 0.0466 | 666.0 | 0.60 / 2.90 | 0.60 / 1.10 | 0.50 / 0.90 |

Memory columns show medians across measured runs. Timing columns show the median of the per-run medians
and the median of the per-run p95 values. Retained history heap fell by 86.5% for 257 traces and 99.6% for
8,193 traces. Dense-case Undo had the same median and a lower p95. The sparse-case Delete p95 increased
by 0.10 ms, and its whole-browser peak RSS increased by 7.5 MiB. These measurements describe this
small-edit workload. Whole-browser RSS includes allocations outside the history.

In both versions, the full history kept 30 steps, 1,080 changed pixels and 30 shared overlap lists at the
initial and final checkpoints. All measured runs verified the affected pixels, overlap order and final
state after reopening. The browser smoke test additionally checks detection undo, grouped class assignment
and merge, exact interval results and restoration of a project with trace IDs stored out of order.

## M1.1.4 native redo

The [V0.104 report](M1.1.4-v0.104.json) records one warm-up, five measured runs and one separate CPU profile per
case on the same Windows 11 machine, AMD Ryzen 7 7700X, Chrome 156.0.8078.80, Node 22.23.4 and Puppeteer
23.11.1. The report lists the parent commit and the fingerprint of the measured V0.104 inputs.

| Traces | Combined history heap (MiB) | Trace records (MiB) | Browser peak RSS (MiB) | Delete (ms) | Undo (ms) | Redo (ms) |
| ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| 257 | 0.0438 | 0.0226 | 633.6 | 0.30 / 1.40 | 0.20 / 0.60 | 0.20 / 0.50 |
| 8,193 | 0.0371 | 0.0158 | 667.4 | 0.50 / 2.50 | 0.60 / 1.00 | 0.40 / 0.70 |

Memory columns show medians across measured runs. Timing columns show the median of per-run medians
and the median of per-run p95 values. Both mixed histories held 30 steps, 30 trace records, 1,080 changed label
pixels and 15 overlap lists across both directions. All measured runs restored the expected traces and ordered
overlaps, then verified the saved mixed state and empty history after reload. The separate browser smoke test
also covers exclusion masks and grouped class changes.

V0.103's reapply timings measure new deletions. Its heap measurement also uses a different checkpoint,
with all 30 steps on Undo, so the two tables describe different operations and retained payloads.
