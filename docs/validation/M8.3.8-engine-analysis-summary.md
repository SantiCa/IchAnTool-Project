# M8.3.8 - Acceptance measurements of the first engine slice (Windows, development gate)

Raw data: [M8.3.8-engine-analysis-windows-v0.150.json](M8.3.8-engine-analysis-windows-v0.150.json), written by
`node tools/measure_engine_analysis.mjs` (commit, host and every sample are in the file). The slice is the method
`section.intervals/1` called from the desktop program with `SEDCORETOOL_ENGINE_EXPERIMENT=1`, run from source with the bundled
Python 3.12.16 runtime. Host: Windows 11 (10.0.26300), AMD Ryzen 7 7700X (16 logical CPUs), 31 GiB, Electron 45.2.2, Node 22.
This is **development evidence on one computer**: it is not a release-gate result.

Fixtures: the public six-section U1385I-1H example and the generated eight-section 960 x 6400 project of M0.1
(`tools/benchmark.py::make_synthetic`, PCG64 seed 138501), at 2 cm and 1.37 cm.

| Gate (contract §7) | Result | Measurement |
|---|---|---|
| Numerical parity | **Pass** | 6,498 + 7,584 intervals compared with the JavaScript calculation after every cold analysis (6 alternating pairs x 2 interval sizes): 0 differences (exact for counts, bounds, indices and missing values, 1e-9 for floats). |
| Matched timing (reported, not pass/fail) | Engine much slower | Cold analysis of all sections, median of 6 paired fresh-process runs. Public example: engine 4,173 ms (2 cm) and 4,210 ms (1.37 cm) against JavaScript 26.6 and 27.2 ms. Synthetic: 6,889 and 6,846 ms against 110 and 112 ms. Unchanged, cached: below 1 ms for both. One large section (6.1 Mpixel): 55 ms snapshot, 190 ms upload (hash and 24 chunks), 600 ms engine (starting the worker process, importing NumPy, computing; the JavaScript calculation takes 17-28 ms), 10 ms download. |
| Responsiveness | **Pass** | During the 8-section synthetic analysis input-to-next-frame p95 was 17.0 ms with the engine (7.4 s) and 17.3 ms with JavaScript (0.1 s); 60 injected pointer events, gate 100 ms. |
| Cancellation | **Pass** | 5 cancellations of the largest section during the job: acknowledged in at most 6.4 ms (gate 250 ms), terminal `cancelled` in at most 533 ms (gate 2 s). |
| Whole-process memory | **Recorded, cadence not met** | Electron + engine tree 827-939 MiB idle and 892-903 MiB during the synthetic analysis (5 processes). The sampler reached one sample per 0.9 s, not the 25 ms of the contract (PowerShell process enumeration), so peaks of short transfers may be missed. |
| Release and recovery: ten cycles | **Fail** | Page reload, open, analyse, close x 10 after one warm-up: no differences from JavaScript, scratch files constant (111 before and after), engine still `ready`. Closed-state memory went from 821.8 MiB (first) to 931.5 MiB (final): +109.7 MiB, gate +64 MiB. Single closed-state samples ranged 822-1,025 MiB with no monotonic trend, but the gate is not met on this evidence. |
| Release and recovery: kills | **Pass** | Workers ended during a job (2 killed): the sections they served showed `INTERNAL`, the engine stayed `ready`, the next analysis matched the reference. Coordinator ended: all sections showed `ENGINE_UNAVAILABLE`, status `unavailable`, the page stayed responsive, and the JavaScript calculation was not used. The engine does not restart by itself; it stays unavailable until the program is restarted. A save interrupted during a job is covered by `tests/e2e/interrupted-saves.mjs`, not by this tool. |

## Found while measuring

- A section whose inputs changed while its job waited was dropped without a new request and stayed *pending* (6 sections in 5 of 10
  cycles). Fixed in `app/js/engineanalysis.js` (a stale job asks again, `analyzeSections` waits for the newest revision) with two tests.
- A first measurement run compared "cold" analyses that the engine had already computed during project load; the tool now gives every
  cold analysis a new mask version.

## Not measured

macOS and Linux; a clean Windows machine; cold cache after a reboot; saturated CPU; package sizes; the 25 ms memory cadence; the
packaged (installed or ZIP) program, which was run from source here. These stay on the release checklist.

## For the maintainer's decision

Correctness is as required, the interface stays responsive and cancellation is fast, but the first slice is two orders of magnitude
slower than the JavaScript calculation for these inputs (about 0.9 s per large section against 20 ms), and the ten-cycle memory gate
is not met. The cost sits in per-job overhead (a new worker process per analysis, hashing and chunked upload of 24 MB label images), not
in the calculation. Recommendation: correct first (a persistent worker, cheaper transfer, then re-measure memory with a faster sampler)
before M8.4; the experiment stays off by default.
